# Modelo de amenazas

## Alcance y supuestos

Tyrian Companion es un plugin local de Obsidian para escritorio. Consulta la API oficial de Guild Wars 2 (GW2), escribe notas y assets en la bóveda y mantiene estado operativo en IndexedDB. No tiene backend propio, Sync propio, analítica remota, telemetría remota, exportación de soporte ni automatización de cuenta. H8.1/H8.4 fijan el contrato v2, H8.2 mantiene un spike C fuera de `src/` y del paquete, H8.3 acepta provisionalmente Rust, H8.5 implementa el helper aislado y H8.6 un cliente core TypeScript puro también aislado. H8.7 implementa una frontera pura de plan/integridad/proceso inyectado, sin executor. H8.8 añade una política shadow pura de presencia/ausencia y un DTO efímero sin efectos de producto. El plugin distribuido todavía no tiene composición, launcher real, settings/UI ni runtime Mumble activo. Sí existe telemetría **local** de calidad de detección API para poder revisar cómo se propuso o confirmó una sesión.

Obsidian, sus servicios opcionales de Sync, el sistema operativo, la API de GW2, el repositorio/issue
tracker de GitHub y cualquier otro plugin instalado son fronteras externas. El modelo protege contra
filtraciones accidentales dentro del código y las superficies implementadas. No promete
confidencialidad frente a malware local, un plugin con privilegios equivalentes, una bóveda o cuenta
ya comprometida, un reporte humano que ignore la redacción ni un paquete de desarrollo malicioso.

## Flujos de red y credencial

- El token GW2 se obtiene de `SecretStorage` solo al ejecutar una operación que lo necesita. La configuración persistida guarda el **nombre de la entrada**, no el valor del token.
- Toda petición autenticada construida por `GuildWars2Client` va exclusivamente a `https://api.guildwars2.com/v2/...`. El constructor no permite sustituir ese host. La cabecera de autorización se añade después de validar que la ruta es relativa.
- La validación consulta `/v2/tokeninfo`; su identificador, nombre y scopes se materializan transitoriamente al parsear la respuesta. El estado de conexión expuesto al resto del plugin conserva nombre y scopes, pero no el identificador del token ni el token crudo.
- Catálogos y precios públicos también proceden de la API oficial de GW2 y no llevan la cabecera de autorización. H9.1 consulta `/v2/commerce/prices` solo tras opt-in, en lotes secuenciales de hasta 200 ids y bajo el cooldown compartido; no usa GW2Efficiency.
- Los iconos visibles del Inventory Advisor pueden solicitarse al origen exacto
  `https://render.guildwars2.com`. La URL procede del catálogo público y se rechaza si contiene
  credenciales, puerto alternativo u otro origen; la petición no lleva clave, cuenta ni cantidad,
  pero el CDN sí observa la conexión de red del cliente.
- No hay endpoints del proyecto, subida de diagnósticos, analítica remota ni tráfico Mumble activo
  desde el plugin. H8.5/H8.6 implementan servidor y cliente core y H8.7 solo el adapter inyectado,
  pero no existe executor ni composición que abra proceso o socket. Cablearlo exige trust anchor,
  nueva revisión y QA real.
- Cada Refresh del Inventory Advisor reemplaza un único recibo diagnóstico local dentro de la carpeta
  del plugin; una fuente fallida expone como máximo `http|timeout|network`, estado HTTP y espera acotada,
  y su contrato cerrado conserva resultado, duración, calidad y coberturas por pasada/fuente —incluidos
  banco, materiales y delivery separados del núcleo de bolsas y compartido—;
  excluye clave, identificadores de cuenta/snapshot, nombres de personaje, objetos, URLs y cuerpos HTTP.
  No es un log acumulativo, no sale del vault y un fallo al escribirlo no altera la recomendación.
- El formulario de bugs es una superficie humana de GitHub, no un uploader del plugin. Solicita solo
  versión, plataforma, modo/fase y reproducción redactada; una confirmación obligatoria prohíbe clave,
  identidad, ruta local, inventario/snapshot crudo, IndexedDB, notas y salida sin redactar.
- El instalador beta H7.5 es un script local explícito y no forma parte del runtime del plugin. Solo
  acepta un vault/config elegidos, ZIP y checksum regulares sin symlinks; valida el paquete completo y
  sustituye transaccionalmente los tres ficheros gestionados. Lock, identidad `dev+ino`, bytes
  originales retenidos solo durante la operación y hashes detectan un segundo instalador, backups
  alterados o sustituciones durante los hooks antes de operar. Un fallo de cierre revierte antes de
  comunicar éxito. No enumera bóvedas,
  no abre Obsidian, no modifica `data.json` ni imprime rutas. El checksum no autentica al productor: la
  QA debe obtener los tres artefactos del run y SHA de CI señalado por el release owner.

Los errores HTTP se reducen a estado y mensaje estable: no incluyen URL, cabeceras ni cuerpo remoto. La API de GW2 es entrada no confiable; sus respuestas se validan antes de convertirse en modelos o persistirse.

## Inventario de datos, retención y borrado

| Superficie | Datos | Retención y borrado actuales |
| --- | --- | --- |
| `SecretStorage` de Obsidian | Token GW2 crudo | Ciclo de vida controlado por Obsidian y el usuario. El plugin lee el valor de forma efímera y solo selecciona su nombre. |
| Settings (`data.json` del plugin) | Nombre de la entrada secreta, locale, carpeta de salida, personaje preferido, modo/sondeo de detección, opt-in/intervalo/retenciones del histórico de precios y rutas/estado de assets gestionados | Persiste hasta cambiar ajustes, desinstalar o borrar los datos del plugin. La carga elimina campos antiguos de credencial y fuerza su reescritura incluso si también debe retener rutas legacy. Según la configuración del usuario, Obsidian podría sincronizar settings; este proyecto no controla ni ha verificado ese servicio. |
| Estado de conexión en memoria | Cuenta, mundo, fecha de creación, access/scopes y nombre de la key | No se persiste por este estado; se descarta al descargar/reiniciar el plugin o cambiar/desconectar el secreto. El ID del token solo existe durante la validación. |
| `tyrian-companion-session-runtime` | Una sesión activa/recuperable: `accountId`, personaje, inventario/build/wallet inicial y final, deltas, revisión y precios | Se conserva hasta descartar la sesión o limpiarla después de escribir con seguridad la nota. No tiene expiración automática. Los esquemas exactos rechazan campos extra. |
| `tyrian-companion-coordination` | IDs de máquina, instancia y sesión; fences, leases y timestamps | Se sobrescribe o libera durante la coordinación; los leases expiran, aunque el registro local puede permanecer. No contiene token. |
| `tyrian-companion-detection-quality` | Eventos locales, IDs de sesión/propuesta, ventanas, causa y, en propuestas asistidas, `accountId`, IDs de snapshots y ganancias de items | No tiene expiración ni borrado/exportación integral expuestos actualmente. Es telemetría local; nunca se envía por el código inspeccionado. |
| `tyrian-companion-pilot-metrics:<vaultId>` | Perfil local de plataforma y versiones; `sampleRevision` monotónica; ventanas, intervalo de polling y referencias SHA-256 de propuestas; decisiones, causas, timestamps, sesiones completadas, recoveries y su clasificación; revisión de pérdidas silenciosas ligada al entorno/revisión exactos | Puede abrirse vacía y lazy al comprobar si ya existe un perfil; sin perfil devuelve `unconfigured` y los hooks no registran observaciones. Separa cada vault, limita a 10.000 observaciones y no poda automáticamente. Cada mutación real incrementa la revisión e invalida la adjudicación en la misma transacción; una revisión concurrente `stale` no se guarda ni degrada salud. **Limpiar** borra observaciones y revisión; **Desactivar y borrar** elimina además el perfil, pero incrementa y retiene solo el contador generacional no personal para impedir ABA al reactivar. No hay red ni sync propio. Las cuatro exportaciones create-only bajo `exports/` son ficheros del Vault, pueden entrar en Obsidian Sync y no se eliminan con esas acciones. `proposalRef` es vinculable si se conocen los IDs candidatos: seudonimización, no anonimización. |
| `tyrian-companion-confirmation-queue` | Cuenta/sesión/propuesta/snapshot y evidencia de ganancias; decisiones de confirmación | Las propuestas pendientes expiran a las 24 h y los recibos se podan a los 30 días durante el procesado. No existe aún un borrado integral explícito para el usuario. |
| Cache de catálogo | Metadatos públicos de items, monedas y materiales; marcadores de ausencias | TTL: 7 días para items/monedas, 1 día para materiales y 1 hora para ausencias; se admite stale hasta 30 días. No contiene datos personales ni credenciales. |
| `tyrian-companion-price-history` | Snapshots públicos compactos por vault/slot con item id y unit bid/ask; agregados UTC por item/día; watch list; lease/fence | Solo existe tras opt-in. Raw 7 días y diario 180 por defecto, configurables a 2/7/14/30 y 42/90/180/365. Compacta antes de podar. No entra en Vault/notas y no guarda cuenta, token, nombres, rutas ni cantidades de listings. |
| Settings H11.6 | Hasta diez pares de outcome público y cobre entero, marcados como origen manual | Locales al settings del plugin, sin cuenta, token, precio observado ni presets. Vacío significa desconocido; el usuario puede retirar cada valor. No entran en el modelo, economy pack, fingerprint, Vault ni notas. |
| Contrato H8.1 Mumble v2 | Constantes públicas de versión, límites, fuentes, map id 866 y tipos TS | H8.5/H8.6 implementan ambos lados en aislamiento y H8.7 solo prepara el lanzamiento. El contrato exige retención `none` para raw y frames. |
| Contrato H8.4 IPC local | Esquemas, framing, token/nonce, secuencia, cadencia exclusiva sample/heartbeat, calentamiento, plazos y errores declarativos | H8.5/H8.6 lo implementan sin composición productiva; H8.7 no genera secretos ni abre proceso/socket porque no contiene executor. |
| Core H8.6 del cliente | Estado efímero de canal/fuente/actividad y observación shadow `mapId + activity` | Solo memoria bajo `enabled && armed`; shutdown/restart descarta token, nonce, secuencia y observación. No escribe sesiones, stores, Vault, logs ni telemetría. |
| Política shadow H8.8 | Contexto efímero ligado a `accountId`, estado puro de ventana/latch para presencia 5 s o ausencia 60 s en el mapa 866 y un DTO comparativo `limited`/`human_required` | Solo memoria. Cambiar de cuenta resetea el latch; no se encola, persiste, muestra ni conecta a captura o lifecycle. Recovery/degradación descarta evidencia parcial. |
| Frontera H8.7 de lanzamiento | Config efímera, launchers/plan exactos, paquete H8.5 de cinco entradas y capability opaca | No persiste datos ni ejecuta procesos. El host no recibe package/helper path. Diagnósticos solo incluyen código/etapa/retryable, integridad y `unsigned_qa_only`; nunca rutas, PID, exit code, botella, SO, identidad, token, nonce o frame. |
| Spike H8.2 CrossOver | Fuente C no productiva, fixtures sintéticos y un frame efímero por stdout en la futura QA | No se importa ni empaqueta. La prueba automatizada no abre la botella; la prueba real aún no se ha ejecutado. El probe no guarda raw ni frame. |
| Puntero de assets gestionados | Identidad hash de la bóveda, raíz, generación y estado | Persiste para poder actualizar o retirar assets gestionados. No contiene token; la raíz sí puede revelar estructura local a quien ya lea el almacenamiento del plugin. |
| Notas de sesión en la bóveda | Personaje/profesión/build, tiempos, economía, resultados y referencias estables SHA-256 de cuenta/sesión | Se conservan hasta que el usuario las borra. Los hashes estables son seudónimos, no anonimización. Assets gestionados no contienen datos de cuenta. |

Los snapshots completos permiten comparar el antes y el después, pero elevan el impacto de acceso local no autorizado. La implementación minimiza campos en cada parser y no guarda la credencial; aun así, el usuario debe considerar la bóveda y el perfil de Obsidian datos personales locales.

## Amenazas y controles

| Amenaza | Control actual | Riesgo residual |
| --- | --- | --- |
| Token persistido o enviado al host equivocado | `SecretStorage`, migración de settings, operación efímera y host HTTPS oficial no inyectable. El test de frontera ejecuta el cliente y transporte reales y exige host, protocolo y cabecera exactos. | Código nuevo podría crear otro cliente HTTP o leer el secreto fuera del flujo revisado. |
| Token en runtime, stores o notas | Validadores exactos en fronteras de persistencia; pruebas productivas invocan `save`, `saveData` y el writer real con un centinela y exigen rechazo antes de escribir. Descubrimiento recursivo revisa stores/writers nuevos. | El guard es una defensa de regresión, no aislamiento frente a código local malicioso u ofuscado. |
| Duplicación o pisado multi-ventana del histórico de precios | La clave `[vaultId,slotStartMs]`, claim transaccional, lease/fence y commit cercado admiten un solo writer. Un owner stale no puede sobrescribir; reintentar un slot ya capturado devuelve el record existente. | Un proceso local con privilegios equivalentes puede manipular IndexedDB; la disponibilidad puede detenerse hasta que expire el lease o se repare/limpie el store. |
| Filtración o mezcla de inventario de Halloween | El store persiste solo ids/cantidades positivos bajo hash de vault y referencia seudónima de cuenta; no guarda `accountId`, API key ni snapshots completos. Idempotencia y first-seen son atómicos y el cambio de credencial cierra el ámbito. | Los ids y cantidades siguen siendo datos sensibles para un proceso local equivalente. |
| Falso positivo económico o de skin/mini | Rare sin precio exige `no_quote` demostrado; 429/offline/payload inválido no califican y el catálogo tiene cobertura cerrada propia. Cada señal unlock exige cobertura completa de su dimensión; permiso ausente, parcial o error fallan cerrados sin invalidar la otra dimensión demostrada. Una skin aplicada no se confunde con `details.skins[]`. | ArenaNet puede cambiar disponibilidad o semántica; la señal siempre exige revisión manual. |
| Contaminación o duplicación de alertas | Solo una sesión Halloween aceptada habilita vivo. Polling y final comparten `session:<id>`, cola y sello terminal derivado del delta estable; el primer writer multiwindow gana, el final vacío elimina provisional y un vuelo tardío no puede reaparecer. Ack solo sobrevive si el contenido final es subconjunto reconocido. Seen, episode, terminal y meta validan scope/version/payload. El backfill reutiliza inspector/hashes, mantiene v2 parcial, espera antes del vivo y no retrasa `lastObservedAt`. | Episodios distintos pueden alertar de nuevo deliberadamente. Un Vault ilegible o una v3 inválida detiene el aprendizaje en vez de inventar cobertura. |
| Comparación de botín presentada como aperturas | Solo un cierre Halloween finalizado, comparable y confirmado con `open=true` exclusivo entra en la comparación. La UI y el record usan `bagsDisappearedNet`; los 18 outcomes, ceros y razones de exclusión quedan atómicos con el sello y no se reconstruyen desde Markdown. BigInt evita overflow y reproduce la criba. El record nuevo identifica el modelo y el registry conserva snapshots históricos; legacy queda fijado y versiones desconocidas fallan cerradas. | El neto no demuestra aperturas ni causalidad de cada ganancia; actividad externa no declarada puede sesgar la muestra. El modelo comunitario puede quedar obsoleto. |
| Aviso de precio duplicado o basado en historia incompleta | H11.5 solo recibe el puerto local después de captura/compactación H9.1. Exige hoy más los 30 días UTC completos previos, usa p90 nearest-rank y falla cerrado ante huecos, bid null, captura futura o store inválido. La transición below→high, límite diario, cooldown, rearmado y `lastValidCapturedAtMs` se deciden en una transacción multiwindow; un resultado antiguo no pisa la decisión aceptada. Proyección/notice prueban coherencia de umbral y timestamps, y un cambio de cuenta vacía la proyección antes de reabrir el scope estable. | Es una serie local, no historia oficial ni garantía de ejecución al precio bid. Cerrar Obsidian crea huecos que bloquean el aviso hasta recuperar 30 días completos. |
| Valoración personal confundida con datos curados o completos | H11.6 mantiene el overlay fuera del modelo/pack/fingerprints y conserva `liquidOnly` como baseline reproducible. El contrato cerrado rechaza claves ajenas o líquidas, duplicados, extras, origen no manual, cobre inválido y overflow. Solo diez outcomes explícitos producen `complete`; vacío/parcial no produce total, EV ni decisión personal y el ajuste conocido se rotula como límite inferior. Cola rara y jackpots agregados permanecen fuera aun con cobertura completa. | Los importes son criterio manual del usuario, no precios verificables ni garantía de utilidad o ejecución. Una valoración completa puede quedar obsoleta y cambiar la recomendación, que sigue siendo manual. |
| Payload público de precios malformado o parcial | El envelope rechaza ids extra/duplicados y records malformados antes del commit. Las omisiones y lados nulos se persisten como `partial`; 429 usa el cooldown común y fallos transitorios retroceden sin inventar muestras. Nunca se guardan cantidades de listings. | La API pública puede estar desactualizada o temporalmente incompleta; el gráfico representa observaciones locales, no un libro de órdenes histórico ni actividad personal. |
| Store de precios futuro, corrupto, bloqueado o sin cuota | La base dedicada falla cerrada y muestra un estado específico; no existe fallback silencioso a memoria. Compactación y poda ocurren en una transacción e idempotentemente por vault; la poda usa días UTC completos y solo reescribe agregados cambiados. | La recuperación automática de corrupción/cuota no está implementada; aumentar la retención tampoco reconstruye datos ya podados. |
| Fuga por errores, logs o soporte | `HttpTransportError` sanea respuestas. `console.*`, telemetría y sinks arbitrarios siguen prohibidos en fuente productiva: solo la frontera local canónica admite records cerrados. Su serializador aplica allowlist por componente, limita profundidad/tamaño y sanea mensajes, stacks, errores anidados, URLs, rutas, identidades, secretos, cabeceras, cookies y cuerpos raw sin invocar getters. El export explícito vuelve a sanear. El issue form exige contexto cerrado y aceptación de redacción. | Un texto personal no reconocido mecánicamente puede sobrevivir al saneado; el usuario debe revisar el extracto. GitHub, notificaciones y caches quedan fuera del plugin. Un nombre no convencional o sistema fuera de `src` requiere revisión humana. |
| Diagnóstico local indisponible, truncado o desbocado | JSONL append-only bajo `<config-dir>/plugins/tyrian-companion/logs/`; cinco ficheros como máximo, 2 MiB por fichero. La cola es acotada y fail-open, la escritura se serializa, el arranque descarta solo la cola JSON truncada, recupera la secuencia monotónica y expone estado/cuota/descartes para UI. Permisos, cuota o fallo interno degradan el diagnóstico sin bloquear la acción de producto; flush y clear son explícitos. | Un proceso local con privilegios equivalentes puede leer, borrar o modificar los ficheros. El puerto de Vault serializa la concurrencia de una instancia; procesos host independientes no reciben una promesa de lock transaccional. La rotación pierde primero el shard más antiguo. |
| Secreto o credencial real en repositorio/fixtures | El scanner enumera ficheros tracked y untracked no ignorados mediante Git, normaliza rutas multiplataforma y decodifica texto UTF-8/UTF-16 con o sin BOM. Busca claves privadas, formatos conocidos, asignaciones de credencial, Bearer y fixtures con evidencia de secreto. Solo informa ruta y regla. | Es análisis textual: no cubre historia Git, binarios, cifrado, fragmentación/obfuscación ni todos los formatos futuros. No sustituye un secret scanner histórico del servidor. |
| Scanner que deja de vigilar una regla | La suite tiene un positivo por regla, corpus real por Git, encodings, negativos de falsos positivos, redacción de salida, sabotaje individual de cada regla y un scanner always-green. | Al añadir una regla hay que añadir también su positivo y su sabotaje. |
| Helper o core Mumble no revisado o fuera de censo | El censo permite únicamente el contrato TS, los módulos puros H8.6/H8.7/H8.8 y los seis módulos Rust H8.5. La extracción AST no puede ocultar imports con comentarios/trivia; guards positivos fijan imports/capacidades, un único call-site de capability dentro del método hasheado, el hash canónico del adaptador completo, delivery y la raíz nativa completa. | Un nombre deliberadamente oculto o dependencia indirecta todavía requiere review humana y análisis de artefactos de release. No hay aislamiento frente a código local malicioso. |
| Lectura excesiva de Mumble | H8.5 lee solo `uiVersion`, `uiTick`, `context_len` y `context.mapId`; el frame lleva solo versión/nonce/secuencia/tick/map/activity. Tests sintéticos y censo rechazan identidad, coordenadas y PID. | La QA real aún debe demostrar esos offsets/tamaños bajo el mapping efectivo y que ninguna herramienta externa copia más memoria. |
| Tearing o muestra híbrida con tick estable | H8.2 usa loads `uint32` alineados y exige dos candidatos completos idénticos; hasta ocho pares distintos terminan en `unstable_sample`. Fixtures inyectan el mismo tick con map distinto y tearing de word. | No es un seqlock: el writer no coopera y dos híbridos idénticos podrían aceptarse. La señal sigue shadow/no autoritativa y la QA real debe medir el comportamiento. |
| Spike adoptado accidentalmente como producción | Vive solo bajo `spikes/`, no tiene imports desde `src`, no entra en el ZIP de tres archivos y la documentación prohíbe cablearlo o ampliar la allowlist. Un guard censusa sus ficheros exactos y capacidades. | Un cambio futuro de packaging o un copiado manual exige nueva revisión; el scanner actual no trata `spikes/` como fuente productiva. |
| Deriva del helper H8.5 | Rust vive solo en `native/mumble-helper`, target MSVC x64, CRT estático y salida `tyrian-mumble-helper.exe`. La zona `unsafe` queda solo en `win32.rs`, que usa `OpenFileMappingW`/`MapViewOfFile` con `FILE_MAP_READ`; el core lee cuatro words y ocho pares. | La QA real todavía debe demostrar el mapping bajo Windows, Proton y CrossOver; dos híbridos idénticos siguen siendo el límite conocido del filtro best-effort. |
| Cadena de suministro y paquete separado | Cargo.lock fija checksums; el verifier rechaza licencia/source/proc-macro/custom-build desconocidos y valida un staging sintético exacto de cinco ficheros. CI inspecciona PE x64, CRT estático y dos builds, pero solo sube `UNSIGNED-NOT-FOR-RELEASE` un día. Un PDB efímero puede existir bajo `target`, pero staging y artifact rechazan PDB/DLL/LIB/OBJ/RLIB/RMETA. El ZIP del plugin sigue exactamente en tres ficheros. | No existe paquete productivo ni firma; la reproducibilidad de CI debe ser confirmada por el run real y un ZIP declarativo no sustituye análisis de bytes. |
| Binario sin firma o identidad falsa | Authenticode es la firma prevista, `status=pending` y `releaseAllowed:false`; la firma sigue pendiente y no se puede presentar el helper como firmado o publicable. | Incluso tras firmar, SmartScreen/reputación, expiración, custodia de claves y validación bajo Proton/CrossOver necesitan política y QA específicas. |
| Cliente local falso, replay o frame corrupto | Solo loopback numérico, puerto efímero, nonce de 128 bits mínimo, versión exacta, frame máximo 512 bytes, claves cerradas, `initialSequence:0` y secuencia estrictamente creciente. Cualquier desviación se descarta y la API v1 continúa. | Otro proceso con los mismos privilegios podría observar o alterar el canal; el nonce reduce conexión accidental, no sustituye el límite del modelo frente a malware local. |
| Discovery o autenticación local manipulados | H8.4 fija bind `127.0.0.1:0`, bootstrap/ready framed por stdin/stdout y hello/welcome TCP. El helper captura el token CSPRNG de bootstrap y exige exactamente ese valor en hello mediante comparación constant-time; bootstrap no usa expectativa externa. El token vive solo en bootstrap+hello y argv, env, fichero, log, stdout, stderr, discovery, settings, IndexedDB, Vault y telemetría están prohibidos. Nonce CSPRNG se renueva por conexión. Host/puerto/downgrade/token/nonce/conexiones inválidos fallan cerrados. | Un atacante local con privilegios equivalentes que observe stdin/stdout o memoria puede robar la capability; no se promete aislamiento frente a malware local. |
| Desincronización o DoS del canal H8.4 | Heartbeat y sample comparten secuencia exacta `0,+1`; cada llamada debida emite uno y el sample derivado de tick/map raw sustituye heartbeat y satisface liveness. El primer válido no retiene tick; el segundo abre época advancing, y cualquier source-status borra tick/startedAt. 1.499/1.500 ms fijan advancing/stalled sin reutilizar ticks stale. Una llamada tardía emite como máximo uno y agenda desde now, sin catch-up/replay; 2 s sin record válido producen `heartbeat_timeout`, así que sleep 60 s no causa ráfaga. Gap/replay/regresión/overflow/wrap cierran. Fallo pre-ready exige restart; solo post-ready permite reconnect al mismo helper. `helper_exited` invalida token/puerto/nonce/secuencia. La tabla de fases rechaza records fuera de fase; solo el estado lifecycle `healthy` resetea backoff. | Un peer local puede provocar reconexiones o indisponibilidad; el recorrido API-only debe conservarse sin ocultar la degradación. |
| Parser ambiguo o smuggling de records | Un único framing `uint32` big-endian + JSON UTF-8 1..512 se aplica a stdin/stdout/TCP. H8.5 Rust y H8.6 TypeScript aplican la misma frontera: máximo simultáneo 516, UTF-8 fatal, JSON cerrado, extra/missing y duplicados incluso con clave escapada; secretos base64url exigen forma canónica exacta. | La paridad está cubierta con fixtures sintéticos; falta probar ambos extremos compuestos y el transporte real por plataforma. |
| Callback stale, throw o reentrada del host | El cliente H8.6 cerca callbacks por generación, aísla throws de `onState`/`onError` y vuelve a comprobar shutdown tras cada entrega. H8.7 aplaza callbacks inline y cierra el handle si falla ese scheduling. | El executor host real y su interacción con unload de Obsidian todavía no existen ni tienen QA. |
| Manifest/checksum autocontenido confundido con autenticidad o TOCTOU | H8.7 abre el paquete H8.5 exacto, valida manifest y cuatro checksums, y pasa solo una capability opaca ligada a esos bytes/digests; el proceso no puede volver a resolver el EXE por path. Se etiqueta únicamente `integrity_checked` / `unsigned_qa_only`. | Los hashes acompañantes detectan corrupción, no autoría. Un executor futuro debe exigir digest externo aprobado o Authenticode y garantizar que su capability sea un handle/copia privada, revalidada inmediatamente antes de cada spawn/restart. |
| Callback del host durante `spawn` | H8.7 transfiere y aplaza solo un stdout inline de hasta 516 bytes y revalida antes de abrir delivery. Overflow, segundo evento o exit, incluso en la microtask entre retornos, cierran el handle una vez, emiten diagnóstico saneado y notifican exit a H8.6; aplazamiento inline también falla. | El futuro puerto host debe cumplir la semántica asíncrona y probar unload/reentrada con proceso real. |
| Señal local interpretada como verdad o acción | Defaults `enabled:false`, `shadow`, `on_when_armed`, API v1 autoritativa y confirmación humana obligatoria. H8.8 limita el target a 866, acumula 5 s de presencia en idle o 60 s de ausencia durante una sesión ligada y produce como máximo un DTO efímero `limited`/`human_required` por latch, sin cola, persistencia, UI, captura ni efecto de sesión. `activity` solo expresa avance/stall del tick y nunca movimiento/combate/farmeo. | Una fase posterior podría introducir sesgo en ventanas/propuestas; salir de shadow requiere decisión humana, métricas separadas y QA por plataforma. |
| Gap, stalled o recovery contado como presencia/ausencia | Solo muestras aceptadas aportan crédito, acotado a 500 ms por record. Gap, heartbeat/source degradation, `link_stalled`, pérdida de canal y recovery reinician o degradan la evidencia; no existe catch-up y ninguno de esos estados demuestra ausencia. | Los umbrales y falsos positivos/negativos necesitan QA humana con el helper compuesto en las tres plataformas. |
| Señal atribuida a otra cuenta | `accountId` forma parte del contexto de cada señal en idle y en sesión. Un cambio de cuenta resetea ventana y latch antes de aceptar más evidencia; no existe una factory separada que pueda aplicar después una identidad distinta. | El wiring futuro debe derivar la cuenta del estado API autoritativo y demostrar el reset en QA; H8.8 aún no está compuesto. |
| Raw o frame retenido/logueado | Contrato `retention:none`; no se admite settings, IndexedDB, Vault, log ni telemetría para raw/frames. Caída/reinicio invalida nonce, secuencia y estado derivado. | Dumps del proceso o herramientas del SO quedan fuera del threat model local actual. |
| Datos remotos o IndexedDB corruptos | Parsers y esquemas exactos fallan cerrados ante tipos, campos o valores inesperados. | La disponibilidad puede degradarse y requerir limpieza local; no hay reparación automática de todos los stores. |
| Sobrescritura de contenido del vault | Rutas normalizadas, ownership explícito, manifest/bloques con hash y escritura controlada; contenido ajeno no se adopta silenciosamente. | El usuario u otro plugin pueden editar/copiar notas con información sensible; Sync de Obsidian queda fuera del control del proyecto. |
| Sync o soporte futuros y exports locales explícitos | No hay Sync ni exportación automática de soporte. H5.10 y H7.13 solo exportan tras preview/acción humana, con allowlist, saneado, rutas normalizadas y escritura create-only. | Un export ya creado pertenece al Vault, puede ser copiado o sincronizado y no desaparece al limpiar su store de origen. Un módulo con nombre atípico o fuera del árbol inspeccionado exige review manual. Antes de Sync propio deben definirse autenticación, cifrado, retención, revocación, residencia y metadatos. |

## Privacidad y RGPD

El código inspeccionado no crea un responsable/encargado remoto del proyecto: no hay backend propio, analítica remota ni exportación de soporte. Por eso no se puede afirmar ni exigir residencia UE/DPA a un servicio del proyecto inexistente. La relación, residencia y términos de la API externa de GW2 y de servicios opcionales de Obsidian no se han verificado en este lote.

Los datos de cuenta, personaje y sesiones son datos personales o seudónimos cuando pueden vincularse al usuario. El usuario puede inspeccionar/exportar/borrar directamente sus notas y descartar la sesión runtime. H7.13 permite exportar, limpiar o desactivar su journal de piloto, pero una referencia SHA-256 estable continúa siendo seudónima y los exports previos permanecen fuera de ese borrado. El producto **no ofrece todavía borrado y exportación integrales** de detection-quality, coordination y confirmation-queue. Tampoco automatiza la eliminación de backups o copias creadas por Obsidian/Sync. No debe declararse cumplimiento pleno de autoservicio de acceso, portabilidad o supresión hasta cubrir esos stores y documentar el procedimiento.

## Verificaciones no cubiertas

- No se verificaron políticas, residencia, DPA ni comportamiento de Obsidian Sync o de la API de GW2.
- No se ejecutó auditoría CVE ni análisis de dependencias transitivas; el scanner de secretos no cumple esa función.
- No se validó borrado físico del navegador/IndexedDB, copias de seguridad, swap ni memoria del proceso.
- No se probaron malware local, plugins hostiles, manipulación deliberadamente ofuscada ni recuperación forense.
